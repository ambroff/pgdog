* Goal

Use [[https://github.com/jepsen-io/jepsen][Jepsen]] (with Elle for transactional histories) to test, under faults,
the safety properties PgDog claims or implies. For each claim, record one of
three outcomes:

1. *Holds.* No anomalies found under the faults we injected.
2. *Doc gap.* PgDog behaves as designed, but the docs promise more (or are
   ambiguous). Fix the docs.
3. *Bug.* PgDog violates a property it does claim. Record it in the private
   findings report (see [[*Reporting and triage][Reporting and triage]]) with
   the Jepsen test as the reproducer. Regression tests are proposed to the
   PgDog devs as part of the report, not opened as public issues/PRs.

Out of scope: performance, liveness (except where a liveness failure is
really a safety failure, e.g. orphaned prepared transactions holding locks),
and auth.

* Claims inventory

What PgDog says (README.md, docs/, config docs) and what we will check.

| # | Claim / implied guarantee                                                                                                                        | Source                                                    | How we test it                                                         |
|---+--------------------------------------------------------------------------------------------------------------------------------------------------+-----------------------------------------------------------+------------------------------------------------------------------------|

The 2PC docs ([[https://docs.pgdog.dev/features/sharding/2pc/]]) word the
atomicity claim cautiously: cross-shard txns "have a very high chance of being
atomic", and 2PC "provides an /eventual consistency/ guarantee only". Crash
recovery ([[https://docs.pgdog.dev/features/sharding/2pc/crash-recovery/]]) is
marked "new and experimental" and "requires PgDog to run on a machine with a
durable storage medium". So for C4/C5 the bar is: all-or-nothing *once
recovery has finished*, given a durable WAL disk. Part of the job is to put a
number on "very high chance".

Claims PgDog does *not* make, which we must not file as bugs (record them as
"expected anomalies" in the results):

- *No global snapshot across shards.* A cross-shard read can see one shard
  before a 2PC commit and another shard after it. Expect Elle to report
  read-skew / G-single style anomalies on cross-shard reads even with 2PC on.
  The docs say this explicitly: "other clients will be able to see partial
  updates to the database cluster".
- *No strict serializability across shards* (no global commit order).
- *Async replicas are stale.* Reads routed to replicas are not read-your-writes
  unless the docs say so for a given mode.
- *PgDog does not fence an old primary.* It "doesn't replace tools like Patroni".

* Hypotheses from reading the code (unverified)

These are the leads to go after first. Each one needs a Jepsen run that
confirms or rules it out.

** H1: 2PC crash recovery orphans prepared transactions when =NODE_ID= is unset
- The gid is =__pgdog_2pc_[<deployment_id>_]<instance_id>_<tid>=
  (=two_pc/transaction.rs=).
- =instance_id()= is =NODE_ID= if set, otherwise 8 random hex chars generated
  per process (=pgdog/src/util.rs:50=).
- The WAL identity record stores only the numeric =tid= plus user/db
  (=two_pc/wal/record/identity.rs=), not the full gid.
- After a restart without =NODE_ID=, recovery rebuilds a gid with the /new/
  instance id. =cleanup_phase= calls =two_pc(.., ignore_missing = true)=
  (=two_pc/manager.rs=), so the =COMMIT/ROLLBACK PREPARED= for a gid that
  doesn't exist may "succeed" silently. The real prepared txn then stays in
  =pg_prepared_xacts= holding locks, and phase-2 txns are never committed
  (a lost acknowledged write, if the client was acked).
- The existing crash test (=integration/two_pc/crash_recovery.py:112=) sets
  =NODE_ID=, so it wouldn't catch this.
- The docs never tie =NODE_ID= to 2PC. It is documented only on the unique-IDs
  page, as needed for unique ID generation. A user who follows the 2PC and
  crash-recovery docs would not set it. If this is confirmed, it is a bug, not
  a misconfiguration. Possible fixes: persist the full gid (or the instance id)
  in the WAL; refuse to start with 2PC on and =NODE_ID= unset; or have
  recovery also scan =pg_prepared_xacts= for this deployment's prefix.
- Test: kill nemesis on PgDog with and without =NODE_ID=; orphan checker.
- *Confirmed in M3* (F9). One correction: the orphans come only from txns
  the client was never acked for (PgDog acks after phase 2 completes), so
  no acked write is lost. What is lost is atomicity (a txn killed in phase 2
  stays committed on some shards and prepared forever on the others) and
  liveness (the orphans hold their row locks and SIREAD locks for good).

** H2: The 2PC WAL is lost along with the PgDog node
- Each PgDog instance has its own WAL. Nothing else scans
  =pg_prepared_xacts= for another instance's =__pgdog_2pc_*= gids (the only
  other reader is =replication_slot.rs=, which only counts them).
- If a node is replaced (k8s pod rescheduled, WAL on an ephemeral volume),
  its in-doubt txns are orphaned for good.
- Test: kill a PgDog node and bring it back with an empty WAL dir. Also kill
  one node permanently while a second node keeps serving traffic.
- *Confirmed in M3* (F10): same outcomes as H1. The second PgDog never
  touches the first one's gids.

** H3: WAL durability depends on the fsync settings
- =two_phase_commit_wal_fsync_interval= defaults to 0 (flush and fsync on
  each write signal). A non-zero value fsyncs on a timer. Check whether
  =wait_flush()= then returns before the fsync, in which case a phase-2 record
  could be acked to the protocol and lost on a power failure.
- Test: LazyFS under the WAL dir with "lose unfsynced writes" plus a PgDog
  kill, at fsync interval 0 and at 100 ms.
- *Refuted as worded* (M3). A non-zero interval is group commit:
  =wait_flush()= returns only after the =sync_data()= that covers the record
  (=wal/live_segment.rs:211-252=), so no record is acked before its fsync.
  The LazyFS runs at 0 and 100 ms were valid (0 orphans, 0 partial). The
  real durability hole is next to it: WAL write and fsync *errors* are
  swallowed and the txn proceeds as if the record were durable (F11).

** H4: Error on =COMMIT= does not mean "not committed"
- =end_two_pc= returns an error if phase 2 fails partway, e.g. the
  connection to one shard drops after another shard already ran
  =COMMIT PREPARED=. The manager and recovery then finish the commit.
- Postgres clients usually read an error on =COMMIT= (other than a lost
  connection) as a definite abort. If PgDog returns an ordinary
  =ErrorResponse= here, an "aborted" txn becomes visible. Elle reports that as
  G1a (aborted read).
- Test: the Jepsen client first maps COMMIT errors to =:fail= (definite) by
  SQLSTATE, to surface this. Classify the result afterwards: bug or doc gap.
- M1b: already true without 2PC. A lost server connection during =COMMIT=
  reaches the client as =FATAL 58000=, and some of those txns committed
  (F5). The 2PC form (=end_two_pc=) is still for M3.
- *Confirmed in M3* for 2PC (F13): a lost server connection during
  =COMMIT PREPARED= reaches the client as =FATAL 58000=, and the 2PC manager
  then commits the txn on every shard. The docs do say phase-2 errors end in a commit, but the client
  cannot tell a phase-2 error from a phase-1 one (rolled back): both are
  =FATAL 58000= or the server's own error.

** H5: When 2PC actually kicks in
- 2PC runs only if =two_pc_enabled() && route.is_write() && !rollback &&
  transaction.write() && connected_servers() > 1= (=end_transaction.rs:75=).
- Edge cases to probe:
  - Cross-shard writes in autocommit: multi-tuple insert, cross-shard
    =UPDATE=/=DELETE= without =BEGIN=. These depend on
    =two_phase_commit_auto=.
  - A txn whose =Transaction= is classified read-only but contains a write
    (=BEGIN READ ONLY= is rejected by PG, but what about functions?
    =SELECT ... FOR UPDATE=? data-modifying CTEs?).
  - Extended protocol vs. simple protocol =COMMIT=.
- Test: run every cross-shard workload under both protocols, with
  =two_phase_commit_auto= on and off.
- *Resolved in M3.* Simple, extended and named-prepared protocols and
  =SET TRANSACTION= mode all go through 2PC and hold (valid). The gaps are
  elsewhere:
  - =two_phase_commit_auto= is off by default (D1), and then a cross-shard
    autocommit write is not atomic (F15).
  - =transaction.write()= only means "not =BEGIN READ ONLY=", so read-only
    txns spanning shards also run 2PC (N3).
  - =COMMIT AND CHAIN= is parsed as a plain =COMMIT=; under 2PC the chain is
    lost (F14).
  - PgDog-generated errors don't mark the txn failed, so the =COMMIT= after
    them takes the 2PC path and commits (F8, C12).

** H6: Concurrent shard-key updates can duplicate rows
- The rewrite runs SELECT, INSERT (new shard), DELETE (old shard). I found
  no =FOR UPDATE= / locking read on this path (to be confirmed). Two
  concurrent moves of the same row could both read it and both insert,
  which yields duplicates. Separately, without 2PC a crash between the
  INSERT and the DELETE leaves a duplicate.
- Test: shard-key-move workload with high contention on few rows.

** H7: =unique_id= can repeat after a clock step backwards across a restart
- The last timestamp and sequence live only in memory. Within one process,
  =wait_until= handles a clock that goes backwards. After a restart, if the
  clock is behind the last emitted timestamp, IDs can repeat.
- Jepsen's clock nemesis (bump/strobe) plus kill/restart should find this.
  The code comment asks for "reasonably accurate" clocks, but the user docs
  ([[https://docs.pgdog.dev/features/sharding/unique-ids/]]) state no clock
  requirement at all. At minimum this is a doc gap. Measure the bound (how
  far back the clock can step without causing duplicates) so the report can
  propose wording.
- Small extra doc gap: the unique-IDs page gives "e.g., =hostname=" as the node
  identifier, but =NODE_ID= has to end in =-<number>=.

** H8: Split-brain routing with =role = "auto"=
- If the old primary is partitioned from its replicas but not from PgDog,
  and a replica is promoted, two hosts report =pg_is_in_recovery() = false=.
  Which one gets writes? Does PgDog ever write to both, or flip-flop between
  them per =lsn_check_interval=?
- Test: partition-primary-from-replicas + promote nemesis. Elle should see
  lost updates / G0 if writes split across two primaries.

** H9: Session settings leaking across pooled clients weakens isolation
- If =SET default_transaction_isolation= or
  =SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL ...= leaks to,
  or fails to follow, a client across server connections, the client silently
  gets a weaker isolation level.
- Test: session-isolation-leak workload.
- *Confirmed in M1* for =SET SESSION CHARACTERISTICS= (and so for JDBC's
  =setTransactionIsolation=) and for =set_config()=. Plain =SET= /
  =RESET= / startup options are tracked correctly. See F1–F3.

** H10: Resharding cutover window
- The drain reads =pg_current_wal_lsn()= after traffic stop and
  =cancel_all(source_db)=. Questions:
  - What about a txn that was already open when the barrier went up?
  - What about a =COMMIT= cancelled mid-flight (indeterminate)?
  - What about a 2PC txn in phase 2 at cutover?
- =RESHARD= cutover is single-node only (=docs/RESHARDING.md:23=). The manual
  =MAINTENANCE ON= / =RELOAD= / =MAINTENANCE OFF= flow is claimed to be atomic
  across containers. Test both.

** H11: A checkout timeout can leak a pool slot for good
Found by reading the code during M1b. Not reproduced: every M1b pool
drained.
- =Inner::put= (=backend/pool/inner.rs:329=) hands a returned connection to
  the oldest waiter over a oneshot channel and records it in =taken=, under
  the pool lock. The waiter's checkout timeout can fire on another worker
  thread after its last poll of the channel came back empty but before
  =Waiting::drop= (=backend/pool/waiting.rs:13=) takes the lock. The handoff
  then succeeds, =Waiting::drop= has nothing to remove, and dropping the
  channel drops the =Server= without a check-in. The =taken= entry is never
  cleared.
- Each leak makes =total()= / =full()= one too high, so the pool's usable
  size shrinks by one. A =RELOAD= that moves connections into the new pool
  (=Databases::move_conns_to=) carries the leak over; one that rebuilds the
  pool clears it. Once the leaks reach the pool size and the real
  connections have died (e.g. at the next Postgres restart), every checkout
  times out.
- Test: a tiny =checkout_timeout= with a pool far smaller than the client
  count, so many waiters time out right as connections come back. The
  =pools= checker (=SHOW POOLS= after the run) shows a leak as a checked-out
  count that never drains. A deterministic repro needs a delay injected
  between the timeout and =Waiting::drop=.

* Test environment

** Decision: Incus VMs, control node on the host
Use Incus VMs (=incus launch ... --vm=). This is the path Jepsen's own setup
guide documents for Debian 13 (=doc/lxc.md=, "Debian 13/trixie - Incus" and
"Real VMs w/Real Clocks").

Why VMs and not containers: containers (Docker, LXC, Incus without =--vm=)
share the host kernel's clock, so Jepsen's clock nemesis would skew every
"node" (and the host) together. That makes C8/H7 untestable. LazyFS needs
FUSE, which is also awkward in containers. VMs give each node its own clock,
kernel, page cache and fsync behaviour.

Host (control node) setup, done once:
- =sudo apt install incus=, then =sudo adduser $USER incus-admin= and log in
  again; =incus admin init --minimal=.
- *Docker coexistence:* Docker is installed and active on this host. It sets
  the iptables =FORWARD= policy to =DROP=, which breaks the =incusbr0= bridge
  (Jepsen's docs warn about this too). Fix with
  =iptables -I DOCKER-USER -i incusbr0 -j ACCEPT= and
  =iptables -I DOCKER-USER -o incusbr0 -m conntrack --ctstate RELATED,ESTABLISHED -j ACCEPT=,
  persisted with a small systemd unit or =iptables-persistent=. =nodes.sh up=
  checks for these rules and fails loudly if they're missing.
- Install a JDK (21) and Leiningen. Java is already present; =lein= is not.
- Build PgDog on the host with =cargo build --release=. The nodes run the
  same Debian release, so glibc matches and the binary can be uploaded as is.

Nodes are created by a checked-in script, =integration/jepsen/nodes.sh=:
- =nodes.sh up [N=5]=: for each =n$i=, run
  =incus launch images:debian/13/cloud n$i --vm -c limits.cpu=2 -c limits.memory=4GiB -d root,size=20GiB=
  with a cloud-init =user-data= that:
  - Enables root SSH with the host's public key.
  - Installs =openssh-server sudo iptables iproute2 build-essential=. The
    nodes need a compiler because Jepsen builds its clock helper there.
  - Installs =fuse3 libfuse3-dev cmake g++ git= (LazyFS).
  - Installs =chrony=, which the clock nemesis can stop.
  Then it waits for cloud-init, writes =n1=…=n5= into =/etc/hosts= on the host
  and on every node, refreshes =~/.ssh/known_hosts= with =ssh-keyscan=, and
  takes a =clean= snapshot of each node.
- =nodes.sh reset=: =incus restore n$i clean= on every node. Use it whenever
  a run leaves a node wedged (e.g. a clock at a strange value), instead of
  debugging the node.
- =nodes.sh down=: delete the nodes.
- =nodes.sh up --containers=: the same nodes without =--vm=, for fast
  iteration on client and checker code. Results that count come from VMs.

Postgres comes from the PGDG apt repo and is installed by =db.clj=, not baked
into the image, so the Postgres version can vary per run.

** Topology
Jepsen needs a control node plus N DB nodes it can SSH to as root. PgDog and
Postgres run on separate nodes, so we can partition them from each other.

| Node | Role (sharded topology)        | Role (replication topology)  |
|------+--------------------------------+------------------------------|
| n1   | PgDog A                        | PgDog A                      |
| n2   | PgDog B (multi-instance tests) | PgDog B                      |
| n3   | Postgres shard 0               | Postgres primary             |
| n4   | Postgres shard 1               | Postgres replica (streaming) |
| n5   | Postgres shard 2               | Postgres replica (streaming) |

Jepsen's =db/DB= is per-node, so write one =pgdog.jepsen.db= that dispatches
on the node's role. It installs Postgres from PGDG apt, uploads a PgDog
binary built on the control node, and writes =pgdog.toml= / =users.toml=. It
should implement =db/Kill=, =db/Pause=, =db/Primary= and =db/LogFiles=, so
=jepsen.nemesis.combined/nemesis-package= works without changes.

** Client details
- next.jdbc + pgjdbc, connecting to PgDog on n1/n2 (round-robin per
  process). Run the same workloads with =--control= pointed straight at
  Postgres, so anomalies can be attributed to PgDog or to Postgres.
- Protocol matrix: =prepareThreshold=0= (unnamed statements) and
  =prepareThreshold=1= (named prepared statements, which exercises PgDog's
  prepared-statement rewriting), plus =preferQueryMode=simple=.
- Error classification is the most important part of the client:
  - =:fail= only when we know the txn did not commit: SQLSTATE 40001/40P01
    before COMMIT, errors before COMMIT is sent, constraint violations.
  - =:info= for connection loss, timeouts, and anything during COMMIT.
    Exception: the H4 probe mode, where COMMIT errors are deliberately =:fail=.
- Key placement: use =sharded_mapping= list sharding so the workload knows
  each key's shard. That makes single-shard vs. cross-shard txns explicit.
  Repeat the main runs with default hash sharding, to cover the hash path.

** Final generator (every test)
1. Heal all faults, resume paused processes, restore clocks, restart killed
   nodes.
2. Wait for PgDog 2PC recovery. Poll =SHOW TRANSACTIONS= on the admin DB and
   =pg_prepared_xacts= on each shard, with a deadline (e.g. 60 s).
3. Final reads through PgDog *and* directly against each shard. The direct
   reads are ground truth for the final-state checkers.

** Custom checkers
- *orphan-2pc*: after the recovery deadline, =pg_prepared_xacts= has no
  =__pgdog_2pc_%= gids on any shard. Report gids and ages.
- *final-atomicity*: each cross-shard txn writes a unique token to keys on
  several shards. In the final direct read, every token is present on all of
  its shards or on none. =:ok= txns must be present everywhere, =:fail= txns
  absent everywhere, =:info= either way.
- *errored-commit-visible* (H4): any =:fail= txn whose token is visible in the
  final read.
- *staleness*: for replica reads, the distance between the value read and the
  latest acked write at invocation time, in ms and LSN bytes.

** DONE M1b: Plain pooler, server-side faults and Jepsen PostgreSQL 12.3 follow-ups (C1, C2, H4)
M1 only faulted PgDog and the client side. Ideas taken from Jepsen's
PostgreSQL 12.3 analysis ([[https://jepsen.io/analyses/postgresql-12.3]]):
- *Backend faults.* Jepsen killed Postgres processes in random order. A
  pooler sees the same faults as dead server connections. Add a nemesis that:
  - terminates PgDog's server connections with =pg_terminate_backend=,
    choosing them from =pg_stat_activity= by =client_addr= (the PgDog nodes);
  - SIGKILLs one random backend, which makes the postmaster restart every
    session (crash recovery);
  - runs =pg_ctl stop -m immediate=, then a restart.

  Look for:
  - a statement or =COMMIT= that PgDog silently replays on a new server
    connection;
  - acked appends lost, or G1a;
  - an error ending up on a client other than the one whose backend died;
  - a pool that never recovers;

  Errors during =COMMIT= must surface as indeterminate (=:info=); see H4.
- *Stronger models.* On a single node, Jepsen found RR histories "consistent
  with strong snapshot isolation". So with one Postgres behind PgDog, check
  =:strong-snapshot-isolation= at RR and =:strict-serializable= at SER. Both
  add Elle's real-time edges. PgDog is the component most likely to break
  real-time order, e.g. by acking before the server does or by serving a
  stale connection. First re-check the existing M1 histories offline, then
  make these the defaults where they apply (not across shards or replicas).
- *Write and read paths.* Jepsen's append test:
  - spread keys over several tables, chosen by hash of the key;
  - had a second append path besides =INSERT ... ON CONFLICT DO UPDATE=:
    =UPDATE=, check the row count, =INSERT=, then =UPDATE= again on a unique
    violation;
  - read some keys by an unindexed secondary key, which forces a table scan.

  Add them as =append= options: =--tables N=, =--append-path
  upsert|update-insert=, =--read-by pk|sk|mixed=.
- *Fresh inserts.* Every instance of the SSI bug involved an rw-conflict on
  a freshly inserted row, so keep keys rotating. Lower
  =:max-writes-per-key= (32 now) so new rows keep getting inserted.

  susceptible." Sweep =key-count=, =concurrency= and =--pool-size= (pool ≪

  That tells us how short a run can still be a useful regression test for F1.

** F1: =SET SESSION CHARACTERISTICS= (JDBC =setTransactionIsolation=) is not tracked; txns silently run at a weaker isolation level
1. *Claims:* C2 (session state follows the client) and, as a consequence, C1
   (same isolation as Postgres).
2. *Severity:* isolation violation (wrong isolation level, Elle anomalies),
   plus session state leaking between clients.
3. *Reproducer:*
   =lein run test --nodes n1,n2,n3,n4,n5 -w append --isolation serializable --isolation-mode session --neighbors --concurrency 10 --time-limit 120=.
   Half the clients ask for SERIALIZABLE per session via
   =Connection.setTransactionIsolation=, which pgjdbc sends as
   =SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL ...=. This is
   what Spring's =@Transactional(isolation = ...)= and HikariCP's
   =transactionIsolation= do. The other half share the pool and set READ
   COMMITTED the same way. No faults needed.
   Smaller repro: =-w session-leak --session-mechanisms reset,characteristics=
   (or =reset,jdbc=).
4. *Evidence:*
   - Serializable: Elle =:anomaly-types (:G-single-item :G2-item)=; 271 of
     6198 ok txns report =transaction_isolation = 'read committed'= from
     inside the txn. An Elle cycle contains txn 3453 (=[[:r 271 nil] [:r 269 [2]] [:append 269 4]]=,
     =:isolation-seen "read committed"=).
     =pgdog-pooler-append-serializable-session-iso-neighbors/2026-11-19T23:29:24=.
     Control (=...-neighbors-control/2026-11-19T23:32:01=): Elle valid, 6238/6238
     serializable.
   - Repeatable read: Elle =(:G-single-item :lost-update)=; 241 of 6158 ok
     txns at read committed. =...-repeatable-read-session-iso-neighbors/2026-11-19T23:34:34=;
     control valid.
   - Same client mix with =SET TRANSACTION= per txn: valid, 6110/6110
     serializable (=pgdog-pooler-append-serializable-neighbors/2026-11-19T23:39:41=).
   - =session-leak=, =reset,characteristics=: 1468 mismatches in 30 s, e.g. a
     client that asked for repeatable read saw read committed, and a client
     that ran =RESET= saw =serializable= (another client's setting).
     Same with =query_parser = "on"= (1373) and =reset,jdbc= (1340).
5. *Root cause:* =pgdog/src/frontend/router/parser/query/set.rs:19=.
   =VAR_SET_MULTI= (=SET TRANSACTION ...= and =SET SESSION CHARACTERISTICS ...=)
   becomes a plain =Command::Query=. It runs on whatever server connection
   the client holds, is not recorded in the client's parameters, and doesn't
   mark the server dirty, so it stays on that server connection for the next
   client and doesn't follow this client to its next server connection.
6. *Suggested fix:* treat =SET SESSION CHARACTERISTICS AS TRANSACTION
   ISOLATION LEVEL x= / =READ ONLY|WRITE= / =[NOT] DEFERRABLE= as
   =SET default_transaction_isolation= / =default_transaction_read_only= /
   =default_transaction_deferrable= (that is what Postgres does internally),
   i.e. a tracked =Command::Set=. Keep =SET TRANSACTION= as a passthrough.
   *Regression test:* in =test_set.rs=, expect
   =SET SESSION CHARACTERISTICS AS TRANSACTION ISOLATION LEVEL SERIALIZABLE=
   to produce =Command::Set= with =default_transaction_isolation=; plus a
   Python integration test: two clients on a 1-connection pool, one runs
   =SET SESSION CHARACTERISTICS ... SERIALIZABLE=, the other checks
   =current_setting('transaction_isolation')=.

1. *Claim:* C2.
2. *Severity:* session state leak between clients (any GUC, e.g. an RLS
   tenant id set with =set_config('app.tenant_id', ..., false)=), and lost

3. *Reproducer:* =-w session-leak --session-mechanisms reset,set-config=.
4. *Evidence:* 3736 mismatches in 30 s; =RESET= clients saw another client's

** F3: =set_config()= with bind parameters is never tracked, even with =query_parser = "on"=
1. *Claim:* C2.
2. *Severity:* as F2. This is the usual way an application sets a

2. *Severity:* session state leak between clients.
3. *Reproducer:* any F1–F3 run; look at the =:reset= / =:set= / =:startup=
   rows of =:by-param+mechanism=.
4. *Evidence:* tracked mechanisms alone pass, also under every fault

   =...-reset+set+startup-kill-pgdog+...+partition/2026-11-19T23:02:57=). Mixed

** F5: A lost server connection during =COMMIT= comes back as SQLSTATE 58000, not a connection error
Found at =f8738bda0d41= (same PgDog source as F1–F4).
1. *Claim:* transparency ("neither know there is a proxy in between") and
   H4. Postgres clients treat a lost connection during =COMMIT= (pgjdbc:
   SQLSTATE 08006; the server's own =57P01= / =57P02=) as "outcome unknown"
   and any other error as a definite abort. Through PgDog the lost connection
   arrives as an ordinary =ErrorResponse=, =FATAL 58000=
   (=system_error=), so a client that classifies by SQLSTATE treats a
   committed txn as rolled back.
2. *Severity:* atomicity as the client sees it: an acked-as-failed txn that
   committed. A client that retries on that error applies the write twice; one
   that reports failure lies to its user. No data is lost inside Postgres.
3. *Reproducer:*
   =lein run test --nodes n1,n2,n3,n4,n5 -w append --concurrency 20 --rate 1000 --time-limit 180 --strict-commit-errors --nemesis terminate-backend,kill-backend,restart-postgres --nemesis-interval 4=.
   =--strict-commit-errors= makes the client do what an SQLSTATE-based
   client does: every error on =COMMIT= except 08xxx / =57P01= / =57P02= /
   =57P03= / a dropped socket is a definite =:fail=.
4. *Evidence:* Elle =:anomaly-types (:G1a :dirty-update)=. Of the 4 =COMMIT=
   errors with SQLSTATE 58000 (=FATAL: net: connection closed by peer= ×3,
   =FATAL: net: io: Connection reset by peer (os error 104)= ×1), 3 later
   turned out committed: e.g. txn 34982 =[[:append 2729 6]]= failed at 40.70 s,
   56 ms after a =restart-postgres=, and txn 35005 read =[1 4 5 6]= for key
   2729. The 6 =COMMIT= errors that carried the server's own =57P01= are
   =:info= and harmless.
   =pgdog-pooler-append-serializable-strict-c20-t180-terminate-backend+kill-backend+restart-postgres/2026-11-20T02:34:25=.
   Control with the same classification (=...-strict-c20-t180-control-.../2026-11-20T02:37:51=):
   valid, because pgjdbc reports the dropped socket as 08006 itself.
   Reproduced with =--nemesis kill-backend,restart-postgres= only: G1a +
   dirty-update again, 7 of the 9 =COMMIT= errors with 58000 committed;
   control valid
   (=...-strict-c20-t180-kill-backend+restart-postgres/2026-11-20T03:46:54=,
   =...-control-kill-backend+restart-postgres/2026-11-20T03:50:29=;
   =store/matrix-20261120T034648.tsv=).
5. *Root cause:* =pgdog/src/net/messages/error_response.rs:316=
   (=ErrorResponse::from_client_err=). When the client's server connection hits
   EOF or a reset (=Backend(backend::Error::Net(..))=, message
   =net: connection closed by peer=; it can't be the client's own socket,
   since the client received the message), the client loop
   (=frontend/client/mod.rs:537=) sends =FATAL= with code 58000 for every error
   except =ExecutionError= and admin termination. When the server dies
   without sending its own =57P01= (SIGKILL, =pg_ctl stop -m immediate= before
   the backend writes, network loss), the client only ever sees 58000.
6. *Suggested fix:* when the server connection is lost while a client request
   is in flight, send SQLSTATE =08006= (=connection_failure=), or close the
   client socket without an =ErrorResponse= and let the driver raise its own
   connection error. Keep 58000 for PgDog's own definite errors.
   *Regression test:* unit test that =from_client_err= maps
   =Backend(Net(UnexpectedEof | ConnectionReset ...))= to an 08xxx code; plus
   an integration test that sends =SIGKILL= to a server connection's backend
   while a client waits on =SELECT pg_sleep(10)= (so Postgres sends no
   =57P01=), and checks the client's SQLSTATE is 08xxx.

** F6: =RELOAD= / =RECONNECT= under load can deadlock a sharded cluster until the next =RECONNECT=
Found in M2 at =7523f83= (PgDog v0.1.65). Sharded clusters only.
1. *Claims:* availability. =RELOAD= is how config changes are applied, and
   it is a step of the resharding cutover (=MAINTENANCE ON=, =RELOAD=,
   =MAINTENANCE OFF=, README "Re-sharding", =README.md:570-572=); nothing
   warns that it can deadlock a sharded cluster under load. Relevant to M7
   (C11), which runs that cutover under =append= load. Not a data-safety
   violation (Elle, lost-appends, placement valid), but see severity.
2. *Severity:* stuck locks and outage. Clients hold server connections
   =idle in transaction= indefinitely, with their row locks. Every new
   transaction on that PgDog then blocks at =BEGIN= (cluster-wide, all
   shards); clients already in a transaction get =FATAL 58000 checkout
   timeout=. It lasts until someone runs =RECONNECT=, and =RECONNECT= itself
   can recreate it. No timeout applies (=query_timeout= defaults to unlimited).
3. *Reproducer:* Jepsen =-w append --mode sharded --concurrency 20 --rate 1000
   --time-limit 120 --nemesis admin= (=RELOAD= / =RECONNECT= every ~5 s): 2 of
   4 runs wedged. Deterministic, pool size 1:
   =bash integration/jepsen/repro/sharded.sh setup && ... reload-wedge=; the
   script's comment has the timeline (A holds shard 2; B is in a txn with no
   connection; =RELOAD=; B reads shard 2, queues behind the schema loader; the
   loader's checkout times out and re-queues behind B; A commits, its
   connection goes to B; B's next statement hangs).
   Result (19:10:46Z, 3 shards, pool size 1): B's second read never
   returned (killed by the script's 40 s timeout); a new client C's =BEGIN=
   + read on shard 0 (another shard) hung for its whole 15 s; =SHOW POOLS=
   for shard 2: =cl_waiting 1, sv_active 1, sv_idle_xact 1, healthy f=; the
   log repeated =error loading schema for shard 2: all replicas down= at
   19:11:01, :11, :21 while the health checks to n5 succeeded.
4. *Evidence:*
   - =pgdog-sharded-append-serializable-c20-t120-admin/2026-11-20T08:48:07=:
     on n2, shard 0 stuck from a =RELOAD= at 16:49:13Z until a =RECONNECT= at
     16:49:40; then shard 2 stuck from the =RELOAD= at 16:50:16Z to the end of
     the run. Log: =ERROR error loading schema for shard 2: all replicas down=
     every ~10 s while n5 was healthy. =SHOW POOLS= after the run: n5 pool
     =sv_active 4, sv_idle_xact 4, cl_waiting 1, healthy false=; 8 final
     reads failed.
   - =.../2026-11-20T10:30:47= (harness with no catalog queries, so every
     txn single-shard): n1 stuck on shard 1 from the =RELOAD= at 18:32:39Z; the
     =RECONNECT= at 18:32:40 re-wedged it (the 4 new connections all went to
     clients already in transactions).
   - Never seen in pooler mode (M1/M1b ran =RELOAD= / =RECONNECT= under load):
     schema loading is on only with more than one shard
     (=cluster.rs:661-667=).
5. *Root cause* (found by code reading, confirmed independently by six
   reviewers against both runs): a cycle between clients and the per-shard
   schema loader.
   - A client in a transaction whose first checkout (or a later one, for an
     extra shard) happens after the reload finds the old pool offline;
     =ClusterConnection::get_conn= (=cluster_connection.rs:146-166=) calls
     =safe_reload= and silently moves the transaction to the new =Cluster=,
     then checks out from the new pool. Nothing waits for the new cluster to
     be ready first.
   - On its next statement, =cluster_check= (=route_query.rs:23-68=) skips the
     online check because the client is in a transaction (line 31) but awaits
     =wait_ready()= on the new cluster (lines 55-63), holding its connection,
     bounded only by =query_timeout= (unlimited).
   - Readiness waits for the schema on every shard (=cluster/launch.rs:109-117=).
     The loader (=cluster/schema_loader.rs:70-99=) checks out through
     =primary_or_replica= (=shard/mod.rs:93-97=) in the same FIFO queue as
     clients; after a checkout timeout it re-queues at the tail. Once
     =pool_size= such clients hold a shard's connections, the loader never gets
     one, and the cluster is never ready.
   - =RELOAD= also hands the old pool's taken set to the new pool
     (=pool_impl.rs:316-345=), so the new pool starts full and the loader gets
     only connections forwarded from old transactions, in FIFO order.
     =RECONNECT= releases a wedge (=Cluster::shutdown= marks the old cluster
     ready, =launch.rs:66-72=), but the clients it releases are already in
     transactions on an offline cluster and stampede into the new pools,
     re-running the race.
   - Why my first, simpler repro did not wedge: a client that already holds a
     connection keeps its old =Cluster= (a =Direct= binding never calls
     =get_conn= again), and a shut-down cluster counts as ready.
6. *Suggested fix* (break at least one edge):
   - Don't wait for readiness while holding server connections: in
     =cluster_check=, skip =wait_ready= when the backend is connected or the
     client is in a transaction (readiness was checked at =BEGIN=), or wait
     only on the cluster the transaction started on.
   - Don't move a transaction to a new cluster silently: after =safe_reload=
     in =get_conn=, either wait for readiness before checking out (holding
     nothing), or fail the statement with a retryable error.
   - Give internal work its own connections: have the schema loader (and
     =Oids::load=) use a standalone connection like the health check, or a
     priority checkout, and don't re-queue at the tail after a timeout.
   - Bound =wait_ready= with a finite timeout and return an error on expiry.
   *Regression test:* the pool-size-1 sequence above as an integration test:
   B's second statement must complete (or fail) within a few seconds.

** F7: A txn that grows from one shard to several can deadlock with another txn on the pools; one client is killed after =checkout_timeout=
Found in M2 at =7523f83= (PgDog v0.1.65), no faults needed.
1. *Claims:* availability of single-shard and cross-shard txns; not a
   safety violation (Elle, lost-appends and placement were valid throughout).
2. *Severity:* liveness / availability. Under contention the deadlocks
   repeat: up to 145 =FATAL: checkout timeout= disconnects in 120 s and
   throughput down to 4% of the control (RC). Clients see an unexpected
   =FATAL 58000= and lose their connection; each stall holds row locks for
   =checkout_timeout= (5 s).
3. *Reproducer:* =bash integration/jepsen/repro/sharded.sh setup= then
   =... checkout-deadlock=. Pool size 1 per shard. A: =BEGIN; SELECT v FROM
   append WHERE k = 1= (shard 0). B: =BEGIN; SELECT v FROM append WHERE k =
   1000001= (shard 1). Both then send =SELECT v FROM append WHERE sk = ...=
   (no shard key, so broadcast). Both block; after 6.0 s PgDog sends B
   =FATAL: checkout timeout= and drops it, and only then does A proceed.
   Jepsen: =-w append --mode sharded --read-by sk --concurrency 20 --rate 1000=,
   any isolation level.
4. *Evidence:* no-fault runs with reads by sk:
   SER 73 checkout timeouts, 22k ok vs 83k for the control
   (=pgdog-sharded-append-serializable-read-sk-c20-t120/2026-11-20T09:36:02=);
   RR 104, 24k vs 80k; RC 145, 2.7k vs 75k
   (=...-read-committed-read-sk-c20-t120/2026-11-20T09:46:47=); re-run with
   the unqualified builder: =...-serializable-read-sk-c20-t120/2026-11-20T10:38:33=. The same
   reads with =SET TRANSACTION= first (every txn takes all shards up front,
   in shard order): 0 timeouts, 53k (SER) and 43k (RC) ok
   (=...-serializable-set-txn-read-sk-c20-t120/2026-11-20T10:41:09=,
   =...-read-committed-set-txn-read-sk-c20-t120/2026-11-20T10:43:47=).
5. *Root cause:* =MultiShardUpgrade::upgrade=
   (=backend/pool/connection/multi_shard/upgrade.rs:27-90=) keeps the txn's
   current server checked out while =get_conns_for_shards=
   (=cluster_connection.rs:95-118=) checks out each missing shard in turn, each
   waiting up to =checkout_timeout=. Two txns that started on different shards
   and both need the other's shard wait for each other (hold-and-wait across
   pools, acquired in different orders). =get_conns= for =Shard::All= from
   an empty binding goes in shard order, which is why =SET TRANSACTION= txns
   don't deadlock among themselves. Inside a txn a checkout failure is not
   recoverable (=frontend/client/query_engine/connect.rs:72-98=): the client
   gets =FATAL 58000= and is disconnected. Any statement that broadcasts
   inside a txn triggers this: reads without a shard key, =SAVEPOINT= /
   =RELEASE= / =ROLLBACK TO=, =SET TRANSACTION=, and catalog queries routed to
   the sticky shard (N2).
6. *Suggested fix:* the held server can't be released once the txn has used
   it, so the options are: on an upgrade checkout timeout inside a txn,
   return an ordinary =ERROR= (txn aborted, client connection kept) instead
   of a =FATAL= disconnect, with a shorter, separate upgrade timeout; and/or
   detect the wait-for cycle and fail one side immediately. Avoiding the
   upgrade where possible also helps: route =SAVEPOINT= / =RELEASE= /
   =ROLLBACK TO= / =SET TRANSACTION= and catalog reads to the shards the txn
   already holds (N1, N2). At minimum
   document that mixing direct and broadcast statements in one txn can stall
   for =checkout_timeout= under load.
   *Regression test:* the two-client sequence above with =default_pool_size = 1=:
   both txns must complete (or one must get a non-fatal error) well before
   =checkout_timeout=.

** N1: Isolation and savepoint statements turn every txn into an all-shard txn
Design note for the report (not a correctness bug). =SET TRANSACTION ...=,
=SET SESSION CHARACTERISTICS ...=, =SAVEPOINT=, =RELEASE= and =ROLLBACK TO=
route to every shard (=router/parser/query/set.rs:19-24=,
=query/transaction.rs:25-29, 58-66=). pgjdbc's usual pattern
(=setAutoCommit(false)=, then =SET TRANSACTION ISOLATION LEVEL=) therefore
opens and commits a txn on every shard: 2.99 Postgres txns per client txn in
M2, against 0.98 with =BEGIN ISOLATION LEVEL ...=. Isolation stays correct.
Costs: a server connection per shard for the whole txn; a fault on any
shard fails the txn; F7 exposure; and with =two_phase_commit= on, every
write txn would take the 2PC path (=connected_servers() > 1=,
=end_transaction.rs:76-80=), which matters for M3. Suggest: route these
statements to the shards the txn is already bound to, or buffer and replay
them like =BEGIN=; and document how to keep a txn direct-to-shard.

** N2: Driver metadata queries join the client's sticky shard to the txn
Design note for the report. With next.jdbc's default row builder, pgjdbc's
=ResultSetMetaData.getTableName= runs a =pg_catalog= query on the same
connection, inside the txn. PgDog routes catalog queries to the client's
sticky shard (=system_catalogs = omnisharded_sticky=, =select.rs:270-293=,
=sticky.rs:52=), so the txn joins that shard: =BEGIN ISOLATION LEVEL ...= is
replayed there and the txn commits there. Table OIDs differ per shard, so
pgjdbc's metadata cache keeps missing and the lookup repeats. Effects in M2:
1.07–1.26 Postgres txns per client txn instead of 0.98, and a backend fault
on an unrelated shard aborting txns (2 of 3 "unexplained" lost connections
in the terminate/kill-backend runs; none once the harness stopped the
lookups). With 2PC on, these txns would go through 2PC. Any JDBC stack that
reads result-set metadata (ORMs, generic mappers) behaves this way.
Suggest: route catalog reads inside a txn to a shard the txn already holds;
document it. Investigated with run
=pgdog-sharded-append-serializable-c20-t120-terminate-backend/2026-11-20T09:08:59=.

** F8: An error PgDog generates itself does not abort the txn; the client's =COMMIT= then commits it (C12)
1. *Claim:* C12 ("If we experienced an error and client tries to commit
   transaction anyway, we rollback to prevent cross-shard inconsistencies",
   =end_transaction.rs:53-55=) and C1 (Postgres semantics: after an error
   the txn is aborted, every statement fails with 25P02, =COMMIT= answers
   =ROLLBACK=). With or without 2PC, whenever PgDog's query parser is in use
   (always when sharded; for unsharded clusters only with replicas,
   =query_parser = "on"= etc., =backend/pool/cluster.rs:625-645=).
2. *Severity:* atomicity / isolation violation: writes of a txn the client
   saw fail become visible (Elle G1a, aborted read). Statements sent after
   the error also run and commit.
3. *Reproducer:* =bash repro/two_pc.sh c12-syntax= (and =--2pc off=): =BEGIN=;
   insert on shard 0; insert on shard 1; =SELEC 1=; =UPDATE= on shard 0;
   =COMMIT=. Jepsen: =-w append --mode sharded --cross-shard --two-pc
   --inject-errors 0.2 --inject-error-kind syntax= (20% of cross-shard txns
   send a syntax error in the middle, then =COMMIT= anyway, as a client that
   ignores errors, or an ORM that catches and continues, would).
4. *Evidence:*
   - Repro (=c12-syntax.log=, =c12-syntax-2pc-off.log=): through PgDog
     =SELEC 1= fails with =ERROR: parser: Error parsing query: Invalid
     statement: syntax error at or near "SELEC"=, the =UPDATE= after it
     answers =UPDATE 1=, =COMMIT= answers =COMMIT=, and both rows are on the
     shards (2PC on and off). Straight to Postgres the =UPDATE= fails with
     =current transaction is aborted= and =COMMIT= answers =ROLLBACK=.
   - Jepsen row 11 (2PC on): every injected txn with writes whose =COMMIT=
     returned success committed: 1286 txns failed on the client yet are
     visible; Elle =:G1a :dirty-update=
     (=pgdog-sharded-append-serializable-xshard-2pc-inject0.2-syntax-lt3000-pool20-c20-t120/2026-11-20T12:47:56=).
     Row 12 (2PC off): 1167 injected txns visible (1157 whole, 10 partial);
     the matrix's fail-vis 1186 also counts 19 ordinary commit-time partials
     of 2PC-off. Row 10, the same injection with errors raised by Postgres
     (=SELECT 1/0=, 22012): valid, all 1190 injected txns with writes absent.
     Row 13 (bank, mixed errors) passes only because a transfer's two
     =UPDATE=s run before the injected error and the bank checker sees only
     totals.
5. *Root cause:* =end_transaction.rs:56= rolls back only when
   =context.in_error()=, which is set from the server's =ReadyForQuery=
   status (=query.rs:340-343=) or by error paths that call
   =transaction.set_error()= (some do: =route_query.rs:173-175, 203-205,
   226-228=, =set.rs:46=). Many errors PgDog answers itself don't: parse
   errors (=mod.rs:177-185=, =ErrorResponse::syntax=); in =route_query.rs=
   the =OmniWriteWithDirective= (192), =UnmappedShardKey= (211),
   =DirectShardMismatch= (234) and catch-all (244) arms and the sharding-key
   lookup failures (136-143, 148-152); =query.rs:568-575=
   (=cross_shard_disabled=); =set.rs:193-198=; =mod.rs:164-168= (missing
   prepared statement); =multi_step/update.rs:149-156=. The client is sent
   ='E'= in =ReadyForQuery= (=net/stream.rs:367-382=), so it believes the txn
   failed, but PgDog's state and the servers' txns are still open; later
   statements run (=transaction_error_check=, =query.rs:613-633=, sees no
   error), and =COMMIT= goes through =end_two_pc= or a plain =COMMIT=. PgDog's
   own tests expect Postgres semantics here (=test/lazy_connections.rs=,
   =test/unsupported_aggregation.rs:87= expect 25P02).
6. *Suggested fix:* mark the txn failed in one place: =send_error_response=
   (=query.rs:653-669=) or =error_response= should call =set_error()=
   whenever the client is in a txn. Then the existing =in_error= paths answer
   later statements with 25P02 and =COMMIT= with =ROLLBACK=. Two details:
   - =BEGIN; SELEC 1; COMMIT= with no server connected yet goes to
     =end_not_connected(.., rollback = false)= (=end_transaction.rs:9-41=),
     which answers =COMMIT=; it must answer =ROLLBACK= when =in_error()=.
   - =set_error()= turns =TransactionType::Implicit= (split extended
     requests, =client/mod.rs:663-669=) into an error type; check that such
     an implicit txn is still cleared at =Sync=.
   *Regression test:* in =query_engine/test/=: =BEGIN=, an insert,
   =SELEC 1=, an insert, =COMMIT=; expect 25P02 for the second insert,
   =ROLLBACK= as the =COMMIT= tag, and no row on the server; plus
   =BEGIN; SELEC 1; COMMIT=; one variant per error arm above.

** F9: Without a stable =NODE_ID=, crash recovery resolves the wrong gids: in-doubt txns stay prepared forever, and a txn killed in phase 2 stays half-committed (H1)
1. *Claims:* C4, C5 ("phase-2 txns are committed" after a crash).
   =NODE_ID= is documented only for unique IDs (D4).
2. *Severity:* atomicity violation (a cross-shard txn committed on some
   shards, never on the others) and stuck locks: the orphaned prepared txns
   keep their row locks and SIREAD locks until someone runs
   =ROLLBACK/COMMIT PREPARED= by hand. Writers to those rows block (or hit
   =lock_timeout=), and the orphans hold back =xmin= (vacuum) and block DDL
   on their tables. No acked write is lost: PgDog acks only after phase 2.
3. *Reproducer:* =bash repro/two_pc.sh phase2 --no-node-id= (txn killed
   after shard 0's =COMMIT PREPARED=) and =phase1 --no-node-id= (killed after
   shard 0's =PREPARE=). Jepsen: =--nemesis kill-pgdog --no-node-id=.
4. *Evidence:*
   - Repro (each scenario starts PgDog with =NODE_ID=pgdog-1= and restarts
     it without, i.e. a node whose id changes; with =NODE_ID= unset
     throughout, both ids are random): =phase2-no-node-id.log=: shard 0
     committed, PgDog killed, recovery logged =committing transaction
     __pgdog_2pc_7cc8e913_10418798187623323966= while the real gid is
     =__pgdog_2pc_pgdog-1_10418798187623323966_1=: result PARTIAL (row on
     shard 0 only), shard 1's gid still prepared. =phase1-no-node-id.log=:
     recovery rolled back =__pgdog_2pc_13164ede_507771982111035873=, shard 0's
     =__pgdog_2pc_pgdog-1_507771982111035873_0= stayed prepared. Baselines
     with =NODE_ID= kept (=phase2-baseline.log=, =phase1-baseline.log=):
     committed on both shards / absent on both, nothing left prepared.
   - Jepsen row 18 (=NODE_ID= unset for the whole run): 8 orphaned gids from
     4 txns on all three shards after a 60 s recovery wait (=:orphans=, e.g.
     =__pgdog_2pc_24f452f1_17272550450141096832_0= and =_1=). For each of the
     4 tids the PgDog log has a recovery line under a different random
     prefix (e.g. =recovery committing transaction
     __pgdog_2pc_26cd3673_17272550450141096832=), and n5's Postgres log has
     the matching =prepared transaction with identifier ... does not exist=
     errors that PgDog swallowed
     (=...-2pc-no-node-id-lt3000-pool20-c20-t120-kill-pgdog/2026-11-20T13:11:10=).
     The orphaned txns were prepared on all their shards, so this run shows
     stuck prepared txns, not a partial commit; the partial commit is shown
     by the repro. A final SERIALIZABLE read on n5 (two orphans) failed with
     40001, probably because of them (not proven). Row 17 (=NODE_ID= set,
     same faults): 0 orphans. Bank without =NODE_ID= (row 25, and a
     follow-up with =--nemesis-interval 3=): valid, no recovery line in
     either log, i.e. no kill landed in a 2PC window.
5. *Root cause:* the gid is =__pgdog_2pc_[<deployment>_]<instance>_<tid>_<shard>=:
   prefix in =two_pc/transaction.rs:21-31=, formatted by =Display=
   (=transaction.rs:34-38=) from the /current/ process's =instance_id()=;
   shard suffix in =two_pc/statement.rs:12-43=. The instance id is
   =NODE_ID= or 8 random hex chars per process (=util.rs:50-69=);
   =DEPLOYMENT_ID= (=util.rs:87=) is part of the prefix too. The WAL
   identity record holds only the =tid= (a =u64=, =transaction.rs:8=) plus
   user/database (=wal/record/identity.rs:15-41=). After a restart, recovery
   formats the tid with the new prefix. =cleanup_phase=
   (=two_pc/manager.rs:336-389=) runs =COMMIT/ROLLBACK PREPARED= with
   =ignore_missing = true= (=manager.rs:385=);
   =backend/pool/connection/multi_shard/binding.rs:377= swallows =42704=
   (no such gid); the monitor then calls =done()= (=manager.rs:301-314,
   122-129=), which drops the txn and writes a Remove record.
6. *Suggested fix:* write the full gid prefix (instance and deployment id)
   into the identity record and use it in recovery; or persist the instance
   id in a file in the WAL dir and reuse it on restart (format-compatible).
   Refusing to start with 2PC on and =NODE_ID= unset helps, but does not
   cover a =NODE_ID= / =DEPLOYMENT_ID= that changes between restarts.
   Detect the mismatch: =42704= from /every/ shard for a recovered txn (not
   any single =42704=, which is routine for non-participants) should be
   logged loudly. *Regression test:* =integration/two_pc/crash_recovery.py=
   variant without =NODE_ID= (the existing test sets it, line 112).

** F10: A PgDog that comes back without its WAL (or never comes back) leaves its in-doubt txns prepared forever (H2)
1. *Claims:* C5. The crash-recovery page asks for "a durable disk" and offers
   the Helm =walPvc= option, which covers a pod restarting on the same PVC.
   It says nothing about a WAL that is lost anyway (StatefulSet scale-down,
   a deleted or recreated PVC, a Deployment without =walPvc=, a node that
   never returns), how to find the stranded txns, or how to resolve them.
   This is partly inherent to a coordinator-log 2PC design; the gap is
   detection, tooling and docs.
2. *Severity:* as F9 (partial commits, stuck locks).
3. *Reproducer:* =bash repro/two_pc.sh phase2 --wipe=, =phase1 --wipe=.
   Jepsen: =--nemesis kill-pgdog --wal-mode wipe=.
4. *Evidence:* repro (=NODE_ID= kept, WAL dir emptied before the restart):
   =phase2-wipe.log=: PARTIAL (shard 0 committed), shard 1's
   =__pgdog_2pc_pgdog-1_2653900795219969055_1= still prepared; recovery
   replays 0 segments and logs no commit or rollback. =phase1-wipe.log=:
   shard 0's gid orphaned. Jepsen follow-up (=--nemesis-interval 3=, 38
   kills in 180 s): 11 orphaned gids from 6 txns on all three shards, still
   prepared after the 60 s recovery wait, e.g.
   =__pgdog_2pc_pgdog-2_17395769536334390915_0= and =_1=
   (=pgdog-sharded-append-serializable-xshard-2pc-wal-wipe-lt3000-pool20-c20-t180-kill-pgdog/2026-11-20T14:12:38=);
   no partial commit in that run (the repro shows it). M3 row 19 (7 kills in
   ~90 s) was valid: no kill landed in a window.
5. *Root cause:* each PgDog recovers only from its own WAL
   (=two_pc/wal/recovery.rs=). The only reader of =pg_prepared_xacts= is
   =two_pc/server_transactions.rs:9-19=, called only from
   =backend/replication/logical/publisher/replication_slot.rs:316-322= to log
   a count.
6. *Suggested fix:* at least detect and report: at startup and periodically,
   list =__pgdog_2pc_= gids in =pg_prepared_xacts= older than some bound,
   log/alert them and expose them in an admin command; document how to
   resolve them by hand. Automatic resolution needs more than the gids: a
   gid missing on one participant means either "already committed" (phase 2)
   or "never prepared" (phase 1), and =pg_prepared_xacts= can't tell them
   apart (=phase2-wipe= and =phase1-wipe= look the same there), so "roll back
   unless prepared everywhere" would make a phase-2 partial commit permanent.
   The commit decision must be durable outside the lost WAL, e.g. a marker
   row written inside the prepared txn on a designated participant (its
   commit is the decision) or a coordinator table on a shard, with
   presumed-abort otherwise. A scan for this instance's own prefix must run
   before accepting clients, or exclude its own live gids; two PgDogs with
   the same =NODE_ID= would resolve each other's live txns, so it needs a
   uniqueness check or lease. *Regression test:* the crash test with the WAL
   dir deleted before restart.

** F11: WAL write and fsync errors are logged and ignored; the txn proceeds as if its record were durable
1. *Claims:* C5 and the crash-recovery page's durability requirement: here
   the disk is present but failing (full, read-only remount, EIO). The code
   comments say awaiting means durable (=two_pc/wal/writer.rs:45-48=: "wait
   for it to be flushed to disk. Calls fsync too"; =live_segment.rs:123-125=).
2. *Severity:* atomicity violation after a crash, with =NODE_ID= set and
   the WAL dir intact; silent to clients (acked normally; PgDog logs at
   =ERROR=).
3. *Reproducer:* =bash repro/two_pc.sh enospc=: the WAL dir is a 512 KiB
   tmpfs, filled up; 150 cross-shard txns; then the phase-2 kill. Only the
   write half is reproduced; on tmpfs =sync_data= does not fail, so the
   fsync half is from reading the code.
4. *Evidence:* =enospc.log=: with the WAL tmpfs full, all 150 cross-shard
   txns committed on both shards and were acked normally while PgDog logged
   219 =[2pc] wal writer error: io: No space left on device (os error 28)=;
   the WAL segment stayed at 4 KiB. Then a txn was killed in phase 2 (shard
   0 committed), the disk freed and PgDog restarted with =NODE_ID= and the
   same WAL dir: recovery replayed 0.004 MB and did nothing; result PARTIAL,
   =__pgdog_2pc_pgdog-1_11251868335617765931_1= left prepared on shard 1.
5. *Root cause:* =write_records= (=two_pc/wal/live_segment.rs:211-252=)
   drains the queue first (212), then writes; on a write, flush or
   =sync_data= error it returns early (=?= at 222/225/237) and the queued
   records' =flushed= senders are dropped. The writer loop only logs it
   (=live_segment.rs:198-200=). =Waiter::wait_flush= ignores the
   =RecvError= (=live_segment.rs:54-56=), and =WalWriter::add= returns
   =Ok(())= (=wal/writer.rs:53-63=). So =Manager::transaction_state=
   (=two_pc/manager.rs:153-188=; =wal.add(..)?= at 168-178 and 180), called
   by =phase_one= / =phase_two= (=two_pc/mod.rs:57-72=) before =PREPARE= and
   =COMMIT PREPARED= (=end_transaction.rs:123-134=), never sees an error.
   The =inspect_err= cleanup at =manager.rs:173-178= is dead code for the
   same reason. No other check exists (=SegmentRegistry= has no health
   flag; a failed segment swap is also only logged, =writer.rs:168-173=).
6. *Suggested fix:* send =Result= over the flush channel and fail =add=:
   - A failed identity record must abort the txn before =PREPARE= (client
     gets an error, nothing prepared).
   - A failed phase record must not let =COMMIT PREPARED= start. Note that
     =set_transaction_state= (=manager.rs:164=) moves the in-memory phase to
     Phase2 /before/ the WAL write, and a dropped guard then queues the txn
     for cleanup, which commits Phase2 txns (=manager.rs:258-269, 348-352=);
     set the phase only after the record is durable, or revert it.
   - A failed Remove record (=Manager::done=, =manager.rs:126=) must only be
     logged: the monitor calls =done(..).await.unwrap()= (=manager.rs:313=)
     and =end_transaction.rs:139= would report an error for a committed txn.
   - After a write error the segment may end in a torn record that
     =Segment::load= (=wal/segment.rs:67-104=) would misparse; truncate to
     the last good offset or rotate to a new segment.
   - Don't retry =fsync= on the same file after a failure (Linux may drop
     the dirty pages and report success next time); do what Postgres does
     (=data_sync_retry = off=: crash) or rewrite the record into a new
     segment and fsync that.
   *Regression test:* a WAL unit test with a writer that fails =write_all=
   / =sync_data=; =add= must return an error and no =PREPARE= is sent.

** F12: A =PREPARE= still running when PgDog dies can land after recovery; the txn is left prepared, even with =NODE_ID= and the WAL intact
1. *Claims:* C5 (phase-1 txns are rolled back automatically).
2. *Severity:* stuck locks (one orphan per such txn); no partial commit
   (the txn was in phase 1 and the other shards rolled back).
3. *Reproducer:* =bash repro/two_pc.sh late-prepare=: shard 1's =PREPARE=
   is stalled (deferred trigger waiting on a lock), PgDog is killed and
   restarted, recovery rolls back shard 0 and runs =ROLLBACK PREPARED= on
   shard 1 too (=42704=, ignored); then the stall ends and shard 1's
   =PREPARE= completes. In production the window is a =PREPARE= that is slow
   for any reason: deferred constraint triggers, lock waits (with the
   default =client_connection_check_interval = 0=, Postgres does not notice
   the dead client until the statement ends), or a slow WAL flush on the
   shard. The last one can't be interrupted at all: the prepared txn exists
   but is not yet valid, so =ROLLBACK PREPARED= still gets =42704=.
4. *Evidence:* =late-prepare.log=: shard 1's =PREPARE= stalled
   (=__pgdog_2pc_pgdog-1_7284877293558307058_1=), shard 0 prepared; PgDog
   killed and restarted with =NODE_ID= and its WAL; recovery logged
   =rolling back transaction __pgdog_2pc_pgdog-1_7284877293558307058= and
   shard 0 emptied; then the gate opened (the script checked the =PREPARE=
   was still running). Result: absent on both shards, but
   =__pgdog_2pc_pgdog-1_7284877293558307058_1= stayed prepared on shard 1,
   and an =INSERT= of the same key through PgDog failed with
   =canceling statement due to lock timeout= (the script's =lock_timeout=
   of 2 s; the log's final =exit=1= is that psql).
5. *Root cause:* recovery maps Phase1 to rollback (=two_pc/manager.rs:348-353=),
   sends it with =ignore_missing= (=manager.rs:385=), treats =42704= as done
   (=backend/pool/connection/multi_shard/binding.rs:356-391=, check at 377)
   and then forgets the txn (=manager.rs:312-313=, =done()=).
6. *Suggested fix:* before resolving a phase-1 txn, check =pg_stat_activity=
   on each shard for a running =PREPARE TRANSACTION '<gid>'= (the gid is
   deterministic and sent as a simple query, so it appears verbatim); cancel
   or terminate it, wait for the backend to exit, then re-check
   =pg_prepared_xacts= and retry =ROLLBACK PREPARED=. (PgDog's server
   connections carry no per-instance =application_name=, so matching by
   connection doesn't work.) Re-queueing =42704= results with backoff only
   narrows the window. A periodic =pg_prepared_xacts= sweep (F10) also
   catches it. Operators can set =client_connection_check_interval= (PG14+)
   to abort stalled statements of dead clients sooner. *Regression test:* the
   late-prepare sequence above.

** F13: An error on =COMMIT= of a 2PC txn does not tell the client whether it committed: a phase-2 connection loss is reported as =FATAL 58000=, the same as a phase-1 one, and then committed (H4)
1. *Claims:* transparency, H4; the 2PC form of F5. The docs say phase-1
   errors roll back and phase-2 errors commit, but the client cannot tell
   which phase failed. When the server connection drops without a server
   error (crash restart, immediate stop, TCP reset), both phases produce
   =FATAL 58000= (from =ErrorResponse::from_client_err=,
   =net/messages/error_response.rs:316=, see F5). When Postgres sends its own
   error (e.g. =57P01=), it is passed through, and clients already treat
   those as indeterminate.
2. *Severity:* client-visible atomicity: a txn reported as failed is
   committed. Clients that retry apply it twice.
3. *Reproducer:* =bash repro/two_pc.sh h4= (shard 1 resets PgDog's
   connection after shard 0's =COMMIT PREPARED=). Jepsen:

   --rate 1000 --pool-size 20 --lock-timeout 3000 --time-limit 180
   --nemesis terminate-backend,kill-backend,restart-postgres
   --nemesis-interval 4 --strict-commit-errors=.
4. *Evidence:*
   - Repro: =h4.log=: shard 0 ran =COMMIT PREPARED=, shard 1 reset the
     connection; psql got =FATAL: net: io: Connection reset by peer (os
     error 104)= for =COMMIT=; in the same millisecond PgDog logged =[2pc]
     manager committing transaction __pgdog_2pc_pgdog-1_7457636067096773719=,
     and the txn ended up committed on both shards.
   - Jepsen row 32: 2 txns failed with =FATAL: net: io: Connection reset by
     peer (os error 104)= (58000) on =COMMIT= and turned out committed; Elle
     =:G1a :dirty-update=
     (=...-2pc-lt3000-pool20-strict-c20-t180-terminate-backend+kill-backend+restart-postgres/2026-11-20T13:50:13=).
     (a) op 11631 (process 14), failed at 21:50:50.847Z; n1 logged =manager
     committing transaction __pgdog_2pc_pgdog-1_8398892028686749072= at
     50.841Z; cause: a =kill-backend= on n3 (invoked 21:50:50.708Z) and the
     postmaster crash-restart that followed. (b) op 20695 (process 9), failed
     at 21:51:06.211Z; n1 logged =manager committing= at 06.205Z (its first
     =COMMIT PREPARED= attempt failed and was retried); cause: a
     =restart-postgres= (immediate stop) on n3 invoked at 21:51:06.148Z.
   - The same SQLSTATE covered both outcomes: of 19 =COMMIT=s that failed
     with 58000 in that run, 2 committed; e.g. at 21:50:22.992Z a =COMMIT= on
     n1 failed with the same =Connection reset by peer= and n1 logged
     =manager rolling back transaction __pgdog_2pc_pgdog-1_1577975806608829863=.
   - Row 31, same faults with failed =COMMIT=s classified as =:info=: valid.
5. *Root cause:* =end_two_pc= (=end_transaction.rs:109-143=) returns the
   phase-2 error with =?= (131-134); the client loop turns it into
   =FATAL 58000= (=frontend/client/mod.rs:537=, F5) and disconnects; the
   dropped guards (=two_pc/guard.rs:9-13= → =manager.rs:258-270=) queue the
   txn and, since its in-memory phase is Phase2, the manager commits it
   (=manager.rs:348-352=).
6. *Suggested fix:* after phase 1 has succeeded, the outcome is decided. Either:
   - return success once the phase-2 record is durable and let the manager
     finish =COMMIT PREPARED= (what the docs promise). Caveats: the same
     session's next txn may not see its own write on a shard where
     =COMMIT PREPARED= is still pending (or block on its locks); and the
     record is only durable with a WAL configured (D6) and F11 fixed; or
   - report an "outcome unknown" code (e.g. =08006=) for phase-2 failures
     and document it.
   Phase-1 failures should keep returning the server's error (definite
   rollback). *Regression test:* make one shard's =COMMIT PREPARED= fail with
   a dropped connection while the others succeed (they run concurrently,
   =multi_shard/binding.rs:357-388=), and assert on the client's SQLSTATE.

** F14: =COMMIT AND CHAIN= of a multi-shard txn under 2PC drops the chain: the next txn's writes autocommit, and its =ROLLBACK= rolls nothing back
1. *Claim:* C1 (Postgres semantics of =COMMIT AND CHAIN=).
2. *Severity:* atomicity: statements the client believes are in a txn are
   committed one by one.
3. *Reproducer:* =bash repro/two_pc.sh chain= (=--2pc off= for the
   baseline): =BEGIN=; insert on shards 0 and 1; =COMMIT AND CHAIN=; insert
   on shards 0 and 1; =ROLLBACK=.
4. *Evidence:* =chain.log=: psql shows =COMMIT=, two =INSERT 0 1=,
   =ROLLBACK= with =WARNING: there is no transaction in progress= (PgDog's,
   not Postgres'); both chained rows are on the shards. =chain-2pc-off.log=:
   same statements, no warning, 0 chained rows (Postgres semantics).
5. *Root cause:* =router/parser/query/transaction.rs:31-36= maps every
   =TRANS_STMT_COMMIT= to =Command::CommitTransaction=, dropping the =chain=
   flag (the parser test =test_session_control.rs:156-191= asserts exactly
   that). With 2PC (=end_transaction.rs:76-85=: write txn on more than one
   shard), =end_two_pc= sends =PREPARE= / =COMMIT PREPARED= and never the
   client's text (119-140), then =end_not_connected= fakes a plain =COMMIT=
   and clears =context.transaction= (=end_transaction.rs:17-26=), so the
   next statements autocommit and the =ROLLBACK= is answered by PgDog.
   Without 2PC (one shard, or 2PC off) the client's text is forwarded
   (98-104) and the connected servers chain. By code reading only (not
   reproduced): =COMMIT AND CHAIN= after an error in the txn also loses the
   chain even with 2PC off, because PgDog sends a literal =ROLLBACK=
   (56-73), while Postgres rolls back and starts the chained txn.
6. *Suggested fix:* honour =chain=: after the commit (2PC or not) keep the
   client in a txn (=context.transaction= set, =ReadyForQuery= 'T', a new 2PC
   txn id) with the same characteristics, including ones set later with
   =SET TRANSACTION= (replaying the stored =BEGIN= alone doesn't carry
   those). Or reject =AND CHAIN= with =0A000= at parse time, before any
   =PREPARE=, leaving the txn open. *Regression test:* the sequence above
   with 2PC on; expect 0 rows from the chained txn.

** F15: Cross-shard autocommit writes are not atomic unless =two_phase_commit_auto= is on, and one docs page says it is on by default (D1)
1. *Claim:* C4 as the general settings page states it (=two_phase_commit_auto=
   "Default: true"). The 2PC page says it is "disabled by default", explains
   the cost, and says you don't need it if writes are idempotent; the code
   agrees (=backend/pool/cluster.rs:270-273=, =pgdog-config/src/general.rs:668-670=).
   So the default is intended; the bug is the general settings page.
2. *Severity:* atomicity violation for users who trust that page: a
   multi-shard =UPDATE= / =DELETE= / =INSERT= outside =BEGIN= commits on the
   shards where it succeeded and returns the error from the one where it
   failed.
3. *Reproducer:* =bash repro/two_pc.sh autocommit= (and =--auto on=): one
   =UPDATE ... WHERE k IN (a, b)= moving 10 from an account holding 5 (shard
   0, =CHECK (bal >= 0)=) to one on shard 1. Jepsen: =-w bank --two-pc
   --auto-frac 0.5= (half the cross-shard transfers are such a statement).
4. *Evidence:* repro: =autocommit.log=: the statement fails with
   =new row for relation "acct" violates check constraint "acct_bal_check"=,
   yet the balances go from 5 + 5 to 5 + 15 (the credit committed on shard
   1); =autocommit-auto-on.log=: same error, balances stay 5 + 5. Jepsen row
   14 (auto off): final total 2614 instead of 800. The 490 =:fail= transfers
   (all the =CHECK= violation) kept credits summing to 1805; the other 9 came
   from some of the 12 =:info= ones (lock timeouts), which also committed on
   one shard only. Rows 15 and 16 (auto on; 16 with
   kill/pause-postgres): total conserved, but no transfer hit the =CHECK=
   there (balances stayed ≥ 60), so they only show conservation when one
   shard's part fails by lock timeout or a fault; the =CHECK= case with auto
   on rests on =autocommit-auto-on.log=.
5. *Root cause:* by design when auto is off; the issue is the conflicting
   docs.
6. *Suggested fix:* fix the general settings page; consider a startup
   warning when =two_phase_commit= is on and auto is off. (See N5 for the
   throughput cost of auto in a hot-spot workload.)

** F16: A JDBC batch (one pipeline, one =Sync=) across shards is not atomic, even with =two_phase_commit_auto=
1. *Claim:* C1 / C4. Postgres runs the extended-protocol messages up to a
   =Sync= as one implicit txn when no =BEGIN= was sent, so a batch that
   pgjdbc sends with one =Sync= (as here; pgjdbc inserts extra =Sync=s in
   very large batches) is all or nothing against Postgres.
2. *Severity:* atomicity violation, silent (the client gets the batch error
   and assumes nothing was written).
3. *Reproducer:* =bash repro/two_pc.sh batch= (and =--auto on=), which runs
   =repro/batch.clj=: autocommit on, one =PreparedStatement= batch of three
   =INSERT=s: a new key on shard 0, a new key on shard 1, and a key that
   already exists on shard 1.
4. *Evidence:* =batch.log=, =batch-auto-on.log=: =executeBatch= fails with
   =23505= on entry 2; afterwards shard 0's row is there and shard 1's new
   row is not (it shared shard 1's implicit txn with the duplicate). Postgres
   semantics: neither. The same batch straight to one Postgres leaves 0 rows.
5. *Root cause:* PgDog splits the pipeline at each =Execute=
   (=split.rs:48-58=, =frontend/client_request.rs:351-410=). The first
   =INSERT= opens an implicit txn on shard 0; the shard-1 =INSERT= upgrades
   the binding to multi-shard and keeps shard 0's connection
   (=backend/pool/connection/multi_shard/upgrade.rs:62-74=; the comment at 65
   notes "the server can be in a partially comitted state, e.g., implicit
   transaction"); the =Sync= goes to every connected shard (=query.rs:63-64=,
   =multi_shard/binding.rs:236-283=), and each Postgres ends its own implicit
   txn: shard 0 commits, shard 1 rolls back. Auto 2PC never starts because
   =two_pc_check= (=query.rs:587-611=) needs a single statement that is
   itself cross-shard (=route().should_2pc()=,
   =frontend/router/parser/route.rs:408-410=).
6. *Suggested fix:* when a pipeline without =BEGIN= upgrades from one shard
   to several before its =Sync=, turn it into an explicit txn: inject
   =BEGIN= on the already-connected shard(s) (that keeps the earlier
   statements in it) and on the new one, then finish at the =Sync= with 2PC
   (or =ROLLBACK= on any error). Refusing such pipelines is simpler but
   breaks ordinary multi-shard pipelines. At least document that batches
   across shards are atomic per shard only. *Regression test:* a raw
   Parse/Bind/Execute×3/Sync across two shards with a failing last
   statement, expecting no rows (=test/regression_auto_two_pc.rs= covers
   only one multi-row =INSERT=).

** F17: Resolving an in-doubt 2PC txn needs every shard up: one shard's outage keeps other shards' prepared txns, and the whole cleanup queue, stuck
1. *Claims:* C5, availability.
2. *Severity:* stuck locks on healthy shards for the length of an unrelated
   shard's outage. Applies to post-crash recovery and to runtime cleanup
   (every phase-1 failure or interrupted phase 2 goes through the same
   path). The monitor resolves one txn at a time, each failed attempt costs
   a full =checkout_timeout=, and failures re-queue at the back, so one hung
   shard delays every queued txn.
3. *Reproducer:* =bash repro/two_pc.sh stuck-shard=: a txn on shards 0 and
   1 is killed in phase 1 (shard 0 prepared), shard 2 (not in the txn) is
   paused with =SIGSTOP=, PgDog restarts.
4. *Evidence:* =stuck-shard.log=: 15 s after the restart shard 0's
   =__pgdog_2pc_pgdog-1_9676185952246112898_0= was still prepared; the log
   shows =error cleaning up ... transaction: checkout timeout= followed by
   =recovery rolling back transaction ...=, ~5 s apart (the default
   =checkout_timeout=), the first ~10 s after the restart; 10 s after shard 2
   resumed it was gone.
5. *Root cause:* =cleanup_phase= connects with =Shard::All=
   (=two_pc/manager.rs:379-384=) whatever shards the txn touched, so one
   unreachable shard fails the whole cleanup; on error the txn is pushed
   back on the queue and retried (=manager.rs:301-317=).
6. *Suggested fix:* resolve each shard independently (the per-shard gid
   already carries the shard number, and the decision, rollback for phase 1
   or commit for phase 2, is already durable), only on the shards the txn
   used (record them in the identity record), with per-shard backoff; and
   don't let one txn's cleanup block the queue (resolve concurrently).
   *Regression test:* the sequence above: shard 0 must be resolved while
   shard 2 is down.

** N3: Read-only multi-shard txns go through 2PC
Design note / doc discrepancy D9. The 2PC gate (=end_transaction.rs:75-80=,
commented "2pc is used for cross-shard writes") checks =transaction.write()=,
which is just "not started =READ ONLY=" (=transaction_type.rs:118-120=; the
type comes only from the =BEGIN= options,
=router/parser/query/transaction.rs:42-84=). So a =BEGIN= block that only
reads two shards is finished with =PREPARE TRANSACTION= / =COMMIT PREPARED=
(=readonly-2pc.log=: =BEGIN=, one =SELECT= per shard, =COMMIT= reached both
shards as =PREPARE TRANSACTION '__pgdog_2pc_pgdog-1_14455736225506589247_0'=
/ =_1= and =COMMIT PREPARED=). Costs: one extra round trip and two PgDog WAL
fsyncs per read txn; on each shard an xid and two WAL flushes where a plain
read-only =COMMIT= has neither, and a =max_prepared_transactions= slot
while in flight. These txns are also exposed to F9–F12: an orphaned
read-only txn holds SIREAD locks, =xmin= and its =AccessShareLock=s (which
block DDL / =TRUNCATE= / =VACUUM FULL=). The docs may mean =BEGIN READ
ONLY= (which does skip 2PC); say so. A fix can't rely on the router's
read/write classification alone (=SELECT f()= or =nextval()= write): check
on the server (e.g. =pg_current_xact_id_if_assigned()= per shard) or
prepare only the shards that have an xid.

** N4: A failed 2PC commit always disconnects the client, including routine phase-1 serialization failures
Design note. Any error out of =end_two_pc= (=end_transaction.rs:109-140=,
called with =?= at 85 and =query.rs:345, 359=) propagates through
=Client::client_messages= (=frontend/client/mod.rs:603=) to
=spawn_internal=, which sends the error and closes the socket. For a server
error the client gets the server's own =ERROR= (e.g. =40001= from =PREPARE=)
followed by EOF, not a =FATAL=; drivers then report a broken connection on
next use (pgjdbc 08006) rather than a retryable error on a usable session.
=deferred-fail.log=: a deferred constraint fails at =PREPARE= on shard 1;
psql gets the server's =ERROR=, then "server closed the connection
unexpectedly"; the txn is correctly absent on both shards (with =--2pc off=
it is PARTIAL). Under SERIALIZABLE, 40001 at =PREPARE= disconnected clients
138–647 times per 120 s run (0 at RR and RC). The docs say the client
"receives an error"; the disconnect is undocumented, and Postgres keeps the
session after a failed =COMMIT=. Suggest: on a phase-1 failure, run the
cleanup, send the error and =ReadyForQuery 'I'=, and keep the client.

** N5: No distributed deadlock detection; with Postgres' default =lock_timeout = 0= a cross-shard deadlock hangs forever, and killing the clients doesn't end it
Design note. Two txns that lock rows on two shards in opposite orders wait
for each other across shards; each Postgres sees only half of the cycle.
=xdeadlock.log=: A updates a row on shard 0, then one on shard 1; B the
reverse; =lock_timeout = 0=. Both first =UPDATE=s succeed; at 25 s each shard
has one session waiting on a lock; neither Postgres reports a deadlock; both
sessions are still blocked when the psql clients are killed at 45 s, and
afterwards direct =UPDATE=s of those rows on the shards still time out on
the locks: PgDog does not read the client socket while a statement is in
flight (=frontend/client/mod.rs:597-604=), so the server sessions stay
blocked. In a first run without a client timeout the script was killed by
an outer 10-minute timeout (=xdeadlock-first-run-hung.log=, exit 124). Only
a server-side =lock_timeout= / =statement_timeout= or PgDog's
=query_timeout= (default unlimited, =pgdog-config/src/general.rs:1234-1238=)
breaks it. The M3 Jepsen runs set =lock_timeout = 3s= on the shards for this
reason. With =two_phase_commit_auto= every cross-shard autocommit statement
holds its locks on all shards until all have prepared. In the hot-spot bank
workload (8 accounts, 20 clients) row 15 (auto on) had 336 lock timeouts
against 73 in row 14 (auto off), and 995 ok ops in 120 s against 27,865
(only 29 =BEGIN= transfers and 499 autocommit transfers succeeded);
consistent with frequent cross-shard lock cycles, not proof of them, and
specific to this workload. Citus detects distributed deadlocks. Suggest:
document the need for =lock_timeout= / =statement_timeout= with sharding,
and have a cross-shard wait timeout cancel the server statements.

* Open questions
- Which edition/version is in scope? Some features (e.g. automatic
  =RESHARD= cutover) may be EE-only. Does the Aura contract give access to EE
  builds?
- Postgres versions to cover (the oldest supported plus latest?). Every
  version before the August 2020 minor releases (12.4, 11.9, 10.14, 9.6.19,
  9.5.23) has the SSI bug from Jepsen's 12.3 analysis: G2-item at
  SERIALIZABLE with no faults. On those versions the control itself fails.
  The bug's signature is the same as F1's at SERIALIZABLE, so a PgDog
  anomaly must always be attributed through the control and
  =isolation-checker=, never through Elle alone.
- Ask the PgDog devs during triage: is =NODE_ID= meant to be required for 2PC
  (see H1/D4)? The docs don't say so either way.
